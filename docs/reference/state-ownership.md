# State ownership

Each authoritative state has one server owner. A reader may keep only transient presentation state and must not add precedence, reorder records, infer missing truth or maintain a competing contract.

- `GraphService` owns the graph. `useProjection` is a mirror, and its revision guard is the only ordering arbiter. A client response or stream event must pass the graph contract before reaching that guard; a stale command receives the current projection rather than its rejected snapshot. `GraphStore` is a write-behind copy, never a second owner: it is read once at startup, through the same parser as an import, into `GraphService`, and revisions never move backwards when a graph is replaced. It alone knows whether that copy keeps up: while it refuses or fails to write, it keeps the reason and when saving stopped, and the panel shows that state as `GET /api/graph/persistence` delivers it, never inferring it from the graph.
- The provider runtime owns the selected provider/model pair, verification proof and connection status. Credential presence means configured; only a successful uncached connection test with usable output means verified. The connection panel renders the complete server snapshot. Polling joins an explicit refresh instead of cancelling it, while an explicit refresh may retire stale polling.
- `TokenService` owns counters, reservations and token-budget pause transitions, and it alone writes and rebuilds the accounting journal; the server only reads the file once at start and pins the records as plain data. An API reader applies only the exact transition IDs returned by that owner, and the graph uses compare-and-set so a later status cannot be overwritten.
- `PriceCatalog` owns tariff validities, current selection and history order. The token snapshot projects that catalog; price POST responses trigger the existing reader's refresh rather than install a second snapshot. The Prices tab keeps only drafts and history visibility.
- `EventBus` sanitizes, identifies, orders and retains events before publication. Feeds render the server window as delivered; filtering and visual direction are presentation only.

Form drafts, feed filters and in-progress drag positions are presentation state. They may live in the client while they remain outside authoritative snapshots and never resolve a disagreement between server states.

A reader that arbitrates starts reporting records the server never published: a command response or fallback snapshot installed past the revision guard carries the projection back to a revision the stream has already passed, restoring agents and edges whose removal the server announced and producing a descending revision sequence the server cannot emit, because every emit increments. A feed that merged the authoritative window into the list it already holds would show an event id beside a payload the bus published under a different one, and would fill the gap the window reports as truncated with copies the server no longer retains. The provider snapshot carries no revision at all, so request precedence is its only ordering: polling that aborts the explicit refresh after a verification leaves the badge reporting the connection state read before that call, beside a result line announcing the verdict the badge does not show.
